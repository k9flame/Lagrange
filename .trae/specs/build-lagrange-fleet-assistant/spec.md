# 拉格朗日星际猎人选舰配舰模拟助手 Spec

## Why
最终目标是做一个"自动获取账号角色数据 + 量化模拟单舰/舰队输出 + 智能配舰推荐"的工具。但**数据获取是整个项目的前提，也是最大的不确定性**：官方是否开放角色数据授权、抓包协议是否稳定、官服与 B 服鉴权差异，都尚未验证。因此本次**先做数据获取可行性 Demo**：用最小成本跑通"采集 → 解析 → 展示"闭环，验证通过后再固化最终架构，避免在未验证的基础上过度设计。

## What Changes
- 本次交付 **数据获取可行性验证 Demo**：通过采集通道从**官服 / B 服**获取指定角色的数据（角色信息、蓝图、加点、模块、指挥值），并解析为结构化模型。
- 新增**采集验证链路**：PC 代理抓包（mitmproxy）与 Android 模拟器抓包两种方式均可验证。
- 新增**协议解析与角色数据归一化**模块：识别承载角色数据的接口并归一化为标准模型。
- 新增 **Demo 前端**：以 **iOS 风格 UX** 展示采集到的角色数据，验证数据可用性。
- 产出**验证结论与最终架构建议**（客户端形态、计算引擎语言、采集策略），作为下一阶段立项输入。
- **非本次范围（待 Demo 验证通过后再立项）**：完整舰船知识库、单舰数值计算引擎、舰队战斗模拟、配舰优化器、正式多端客户端。

## Impact
- Affected specs: 新增能力域 `data-acquisition-spike`、`demo-ui`、`spike-report`
- Affected code: 新仓库（采集脚本 + 解析模块 + Demo 前端）
- 主要风险：抓包协议随版本变动、证书信任与模拟器环境、官服/B服鉴权差异、账号安全与合规（只读、风险明示）。

## 架构设计（Demo 版，最终架构待定）

### Demo 链路
1. **采集层**：`mitmproxy`（PC 代理，手机/模拟器 WiFi 代理指向 PC）或 Android 模拟器内置抓包。
2. **解析层**：Python 脚本，筛选业务接口、处理加解密/压缩、归一化为标准角色数据模型（JSON）。
3. **存储层**：本地 JSON / SQLite（Demo 阶段轻量）。
4. **展示层**：Vue3 + TS + Vite 的 Demo 前端，iOS 风格 UI，本地运行。

### 待 Demo 验证后再决策的问题
- 最终客户端形态（PC 桌面 / 移动端 / 二者兼顾）。
- 计算引擎语言（Python / Rust）与运行位置（端上 / 服务端）。
- 采集通道主辅策略（官方授权是否可用、抓包还是模拟器为主）。

## UX 设计规范（iOS 风格）
Demo 前端遵循 iOS Human Interface Guidelines 风格：
- **布局**：大标题导航（Large Title）、分组列表（Inset Grouped）、底部标签栏（Tab Bar）、分段控件（Segmented Control）。
- **视觉**：连续圆角（squircle，卡片 16–20px）、充足留白、系统色板、深浅色自适应。
- **层次**：毛玻璃（`backdrop-filter: blur`）、柔和阴影、层级分明的卡片。
- **字体**：SF Pro 风格（`-apple-system` / `Inter` 近似），字重层级清晰。
- **动效**：弹簧曲线、平滑转场与列表出现动画，交互反馈自然。

## ADDED Requirements

### Requirement: 采集通道验证（data-acquisition-spike）
验证程序 SHALL 打通至少一条采集通道，从官服或 B 服获取指定角色的数据，并说明其稳定性与字段覆盖。

#### Scenario: 代理抓包采集
- **WHEN** 手机/模拟器通过 PC 代理接入并登录游戏、刷新角色相关界面
- **THEN** 程序捕获游戏流量并识别出承载角色蓝图/加点/模块的接口

#### Scenario: 数据结构化
- **WHEN** 捕获到原始报文
- **THEN** 程序解析并归一化为标准角色数据模型（角色信息 / 蓝图列表 / 加点 / 模块 / 指挥值）

#### Scenario: 反抓包处理
- **WHEN** 游戏接口存在加密、签名或压缩
- **THEN** 程序能定位并处理相应机制，或明确记录该接口不可解析及原因

### Requirement: 双渠道验证（channel-support）
验证程序 SHALL 分别验证官服与 B 服，记录两渠道的鉴权方式与数据字段差异，并预留扩展其他渠道的结构。

#### Scenario: 官服验证
- **WHEN** 使用官服账号
- **THEN** 记录登录鉴权方式、可获取字段与稳定性

#### Scenario: B服验证
- **WHEN** 使用 B 服账号
- **THEN** 记录与官服的差异（登录、域名、字段命名等）

### Requirement: 采集结果可视化 Demo（demo-ui）
Demo 前端 SHALL 以 iOS 风格界面展示采集到的角色数据，验证数据的完整性与可用性。

#### Scenario: 展示角色数据
- **WHEN** 解析得到角色数据
- **THEN** 界面展示角色信息、蓝图列表、加点、模块等，支持深浅色模式

#### Scenario: 视觉规范
- **WHEN** 浏览任意页面
- **THEN** 界面遵循 iOS 风格规范（圆角、留白、毛玻璃、SF 风格字体、平滑动效），呈现出优雅的 UX

### Requirement: 验证结论与架构建议（spike-report）
验证程序 SHALL 产出结论，包含可行性、稳定性、字段覆盖、风险，以及最终架构建议。

#### Scenario: 输出结论
- **WHEN** Demo 验证完成
- **THEN** 产出文档化结论：采集可行性、协议稳定性、官服/B服差异、账号风险，以及最终架构（客户端形态 / 引擎选型 / 采集策略）建议

## 后续阶段（非本次范围，供参考）
Demo 验证通过后，再规划完整能力：蓝图知识库、单舰数值计算（对舰/对空/攻城 DPM 与生存指标）、舰队战斗模拟（前中后排、护甲/护盾、命中/闪避、目标选择、治疗/拦截、战报与胜率）、配舰优化器（约束下 Top-N 推荐）、正式客户端。
